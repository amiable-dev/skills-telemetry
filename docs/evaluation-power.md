# How much data before the numbers mean anything

Every figure below is generated by [`eval/power.py`](../eval/power.py) — run `mise run power` to
regenerate, `mise run power-check` to fail if this file has drifted. Nothing here is hand-typed, so
you can change an assumption and see what it does rather than taking a number on faith.

The assumptions are doing most of the work. Read [Assumptions](#assumptions) before quoting anything.

## The two questions need two different tests

**1. Does a skill raise the first-time policy pass rate?** A proportion — a PR either passed its
policies on the first CI run or it did not — compared between a with-skill and a without-skill arm.

**2. Does a skill or harness change tokens per merged PR?** A continuous, strongly right-skewed
quantity compared within developer under a crossover. This one needs a correction for clustering that
the first does not, and that correction dominates the answer.

## Question 1 — first-time policy pass rate

Two independent proportions, two-sided:

```
n per arm = (z[1-alpha/2] + z[1-beta])^2 * [p1(1-p1) + p2(1-p2)] / (p1 - p2)^2
```

Substituting 60% -> 75% at alpha=0.05, power=0.80 (so the z terms are 1.960 and 0.842):

```
(1.960 + 0.842)^2 * [0.60*0.40 + 0.75*0.25] / (0.15)^2
   = 7.849 * [0.240 + 0.1875] / 0.0225
   = 7.849 * 0.4275 / 0.0225  =  149.1  ->  150 PRs per arm
```

*alpha=0.05, power=80%, two-sided, independent arms.*

| baseline | with skill | absolute lift | PRs per arm |
|---|---|---|---|
| 60% | 80% | +20% | **79** |
| 60% | 75% | +15% | **150** |
| 60% | 70% | +10% | **354** |
| 70% | 85% | +15% | **118** |
| 70% | 80% | +10% | **291** |
| 80% | 90% | +10% | **197** |
<!-- /generated -->

Note how fast this degrades. Closing the same 15-point gap from a *higher* baseline (70% -> 85%) is
cheaper than closing a 10-point gap from a lower one, because the variance term shrinks near the
extremes. Chasing small lifts is what makes these numbers explode: 60% -> 70% costs more than twice
60% -> 75%.

## Question 2 — tokens per merged PR

Token counts are right-skewed and have no natural scale, so we work on the ratio scale. The standard
deviation then enters as the **coefficient of variation** (CV = sigma/mu) and no absolute token count
is needed:

```
n_iid per arm = (z[1-alpha/2] + z[1-beta])^2 * 2 * CV^2 / effect^2
```

But PRs are not independent. Two PRs from the same developer resemble each other far more than two
PRs from different developers — same habits, same areas of the codebase, same prompting style. The
**intra-class correlation** (ICC) measures that resemblance, and the **design effect** turns it into
an inflation factor:

```
DEFF = 1 + (m - 1) * ICC          m = PRs per developer per arm
n    = n_iid * DEFF
```

At m=10 and ICC=0.2, DEFF = 1 + 9(0.2) = **2.8**. Nearly three times the PRs for the same answer,
purely because the observations are clustered. This is the single most important line on this page.

| 40% | 151 | 223 | 366 |

### Sensitivity to the assumptions

ICC is the assumption we are least sure of, and the table above shows it moving the answer by 2.4x
across a plausible range. CV matters too, and quadratically:

<!-- generated:cv-sensitivity -->
*Same as above at ICC=0.2, varying only the coefficient of variation.*

| effect to detect | CV=0.6 | CV=0.9 | CV=1.2 |
|---|---|---|---|
| 40% | 99 | 223 | 396 |
| 30% | 176 | 396 | 704 |
| 20% | 396 | 891 | 1583 |

If you take one thing from this page: **the uncertainty on the sample size is wider than the sample
size**. These are order-of-magnitude planning figures, not thresholds.

## A correction worth recording

The first version of this analysis paired at **developer** level: each developer contributes one mean
per arm, and the unit of analysis is the developer-period. That looked reassuring — 71 pairs — but it
is the wrong model. Collapsing a developer's PRs to a single mean discards the within-developer
variation the crossover exists to exploit, and 71 developer-periods is far more work than 396 PRs for
a team of any size.

<!-- generated:correction -->
*Why the first attempt was wrong: pairing at developer level versus PR level with developer as a blocking factor, both for a 30% effect at CV=0.9.*

| framing | unit of analysis | n required | in PRs (10 per dev per arm) |
|---|---|---|---|
| paired by developer (**wrong**) | developer-periods | 71 pairs | 710 |
| PR-level, developer as block | PRs | 396 PRs | 396 |
<!-- /generated -->

Use PR-level observations with developer as a blocking factor — a mixed model with a random intercept
per developer, or a paired analysis on developer means weighted by PR count. The clustered formula
above approximates that.

## Assumptions

| assumption | value used | basis | how to replace it |
|---|---|---|---|
| CV of tokens per PR | 0.9 | typical for right-skewed usage data; **not measured here** | `SELECT stddev(t)/avg(t)` over `session_cost` joined to merged PRs, once ~50 PRs exist |
| ICC by developer | 0.2 | plausible mid-range for developer-clustered engineering metrics; **not measured here** | fit a random-intercept model, or compare between- and within-developer variance |
| PRs per developer per arm (m) | 10 | one fortnight at roughly 5 PRs/week | count it |
| alpha | 0.05, two-sided | convention | — |
| power | 0.80 | convention | raise to 0.90 and every figure grows about 34% |

**Both CV and ICC are assumptions, not measurements.** This project has no local data to fit them: at
the time of writing the warehouse holds a handful of rows from dogfooding. The first useful thing real
data will do is replace these two numbers, and every figure here should be regenerated when it does.

## What is not detectable

Stated plainly, because the tables above can be read as encouragement:

- **Effects below 20% in tokens per PR** need 900+ PRs per arm at ICC=0.2. For most teams that is
  years. Do not design a programme around detecting them.
- **Pass-rate lifts under 10 points** need 350+ PRs per arm. Prefer skills expected to move the metric
  substantially, and treat small movements as noise.
- **Anything at all with fewer than 5 developers.** The design effect is not the binding constraint
  there; the absence of between-developer variation is. Report descriptively.
- **Per-skill comparisons early on.** Invocations divide across skills, so a catalogue of ten skills
  needs roughly ten times the traffic to say anything about any one of them.

The hard floor used throughout this project: **below 30 merged PRs per arm, or fewer than 5
developers, report descriptively and make no comparative claim.**
